# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Do not perform page-preview or visual page checks after changes unless the user explicitly requests them.

Do not automatically open, invoke, or switch to any Review, code-review, design-review, diff-review, or approval interface. Only use a review interface when the user explicitly requests it. Normal local preview and verification may continue without opening a review UI.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

Keep every custom select control and its dropdown arrow on the same horizontal line. The Ant Design icon wrapper (`.anticon`) must be positioned inside `.select-wrap` rather than flowing after the native `<select>`.

Switch rows should expose a narrow clickable switch control; adjacent status text and the rest of the row must not toggle the switch.

Headers inside `group-editor-section` should contain the section title only; do not render descriptive `<p>` text in those headers.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Use「巡查計劃模板」as the user-facing name for the inspection-template concept; keep existing internal IDs, fields, and routes such as `templateId` and `/config/templates` for compatibility.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

The frontline App prototype lives in `app.html` and `src/app/`. Its components and visuals should stay as close as possible to the Yonyou BIP mobile platform: use antd-mobile (the base of BIP's TinperM / yonui-mobile) themed with BIP tokens, primary red `#E60012`, grey canvas, white cards, label-left / value-right form rows and a red primary bottom action bar. No official BIP mobile screenshots exist yet, so the current tokens are inferred; when screenshots arrive, compare screen by screen and replace the tokens there.

In the App permission check screen, keep each `.m-permission-list` item in a two-level card layout: icon, title, step and status in the header; explanatory copy and the full-width action below. Completed items should use a restrained green state instead of retaining the pending action layout.

The current back-office prototype uses explicit demonstration identities/scopes and local versioned rules/audit logs; do not present it as production security or as synchronized IAM/mobile responsibility data. - Basic Data:

An empty object or group scope means the template applies to all of them.

The App inspection form groups template items by item type the same way: a section header per type in order of first appearance, with item numbers running continuously across sections. Submit-time validation errors follow that displayed order.

Extra and supplementary inspections may use any 生效 巡查模板; the add-inspection picker lists only the objects the chosen template applies to.

The back-office Inspection Records pages (`src/inspection-pages.tsx`; pure logic in `src/inspection-rules.ts`; App bridge in `src/inspection-data.ts`):
- **List:** the shared table-shell anatomy, with dedicated filters (code, object, plan, template, inspector, status, result, source, void, submit-date range), sortable columns, a fixed right-side View action, and a note that only completed, non-voided inspections count toward statistics.
- **Data ownership:** back-office inspections live in the shared demo state (`inspectionRecords`). The back office reads App inspections live and never writes into the App's own storage. For an App inspection it keeps only an overlay (void flag, supplements, change log). Standalone back-office inspections and ones joined to a plan are pushed to the App as 未完成. App-origin 未完成 inspections are filled in the App; the back office can only void them.
- **Create:** choose an optional open plan, an object, and one of the App's inspection templates (only they carry input kinds, options and abnormal values). The record is 未完成 and holds a template snapshot, so later template edits never change it.
- **Fill and submit (detail page):** items are grouped by item type. Each shows a required marker, an attachment counter, and abnormal-value actions (new work, link existing work). Attachments are uploaded from the computer; images are downscaled and stored inline, capped per item and per record. Draft save keeps 未完成; submit checks required items, attachment minimums and text length, lists every problem with a jump link, and only then sets 已完成.
- **Limited edits:** a completed inspection can only be supplemented (fill empty items, add attachments, remarks and works) with a reason; existing values are never changed.
- **Void:** void and unvoid need a reason and pass the real `void-inspection` permission check with the demo identity selector (default 區詠珊). Voided inspections stay listed but are excluded from statistics and plan progress.

  - Follow-up status is registered by a person (無需跟進 / 跟進中 / 已完成) and the system never changes it automatically. 跟進中 requires an expected follow-up time, and for a new event it cannot be earlier than now.
  - The location is picked on the map, fills in the address (editable) and derives lat/lng and grid.
  - Attachments are uploaded from the computer through the shared `AttachmentField`.

  - If the event is 無需跟進 the drawer offers to switch it to 跟進中.

The back-office Work Records pages (`src/work-pages.tsx` list, create and SLA config; `src/work-detail.tsx` detail and drawers; `src/work-form.tsx` shared form; pure logic in `src/work-rules.ts`; App bridge in `src/work-data.ts`):
- **Data and clock:** works live in the shared `DemoState.works` that the App also reads and writes. Back-office process logs live in `DemoState.workLogs`; the App's own logs are read live and merged by id, and the App copies back-office logs into its timeline. The work module uses the App's demo clock (`nowText` / `demoNow`, 2026-09-29 12:06), not the real clock, so seed works are not all overdue.
- **List:** the shared table-shell anatomy with dedicated filters (keyword, type, status, group, SLA state, grid, priority, source, duplicate status, void, created-date range) plus quick-mode chips with live counts (soon overdue, overdue, unassigned, awaiting acceptance, reopened, duplicates, mine, voided). The SLA column is computed live.
- **State machine:** actions appear only when valid for the state (新建 跟進 / 重新分派; 跟進中 解決 / 重新分派; 已解決 關閉 / 重啟; 已關閉 重啟; 留言 and 作廢 on any non-voided work; a voided work only 解除作廢; a work merged as a duplicate cannot be reopened). Each status action needs its required text, 解決 needs the work type's attachment minimum, and 重新分派 needs a different group. Every action writes a process log and runs the real permission check with an explicit demo identity selector, preselected to a user who passes.
- **Create:** prefilled from an inspection item or an event (type, summary, address, position, description), or standalone. The execution group is chosen live by `dispatchWork` (object group, dispatch rule, type default, else 待人工分派) and the user may override. Saving checks for suspected duplicates (same top-level type, within 30 m, not closed) and offers to link an existing work, create anyway, or create and merge.
- **Edit:** allowed while the work is not voided and not closed. It changes type, summary, description, address, position, priority and attachments with a diff log, but never the group; only 重新分派 does.
- **Duplicates:** merge mode closes the other works with reason 重複 and sets `masterId`; a merged work shows a banner and the kept work's timeline. Link mode shares a `dupGroup`; after a status action the user may sync the same action to group peers that still have the prior status.
- **SLA:** rules are matched by the work's inspection type, then top-level work type, then a default. Each has four limits (assign, first reply, resolve, complete) scaled by priority. Timing is per round (a reopen starts a new round), and the overall state is written to `work.sla`. `/works/sla` shows the rules read-only. The App keeps its own fixed-hour SLA display.
- **Map:** the work location plus the position of each App operation (derived from the logged distance; back-office operations have no position and are not drawn).

The back-office Grid Management page (`src/grid-pages.tsx`; pure geometry and validation in `src/grid-rules.ts`; live registry in `src/grid-data.ts`):
- **Data model:** a grid is `id`, unique `code`, `name`, `boundary` (GeoJSON Polygon or MultiPolygon in lng/lat), and `status` (啟用 / 停用), as in the ER diagram. The grid list lives in the shared `DemoState.grids`, seeded from the App's original 7 grids.
- **Projection:** GeoJSON coordinates map onto the static map image with the exact inverse of the App's `latLng` formula, so grids, events and works agree. This is a demonstration projection, not real GIS.
- **Source of truth:** the managed grids drive `gridOf` (the App's point-in-grid lookup) in both the back office and the App through a registry that `DemoProvider` keeps in step. The first enabled grid in list order wins, a point on a boundary counts as inside, and no match gives 未歸屬. The seed grids use L-shaped cuts so none overlap while every old first-match result is kept (checked in `tests/grid-rules.test.mjs`).
- **List:** the shared table-shell anatomy. Filters: code, name, and status. Columns: code, name, range summary, area, object count, status, with a fixed right-side Edit action. A list/map toggle; the map view shows every grid that passes the filters (all by default) with labels, disabled grids grey and dashed, layer chips for enabled/disabled grids and objects, and clicking a grid opens a popup with code, status, range, area, the object/event/work counts inside it, a note for disabled grids, and 編輯網格.
- **Create and edit share one range editor:** draw the polygon by clicking the map. Drawn vertices can be dragged (while drawing and after 完成繪製); when editing, the current range's vertices become draggable only after 載入目前頂點. 復原 takes back the last range change (an added point, one drag, 完成繪製, 載入目前頂點 or 清除), so repeated 復原 walks back to the current range; 清除 removes every vertex and, when editing, does not fall back to the current range (復原 restores it). Vertex dragging uses `PlanMap`'s opt-in `onMarkerDrag`/`onMarkerDragEnd` with `draggable` markers; other maps are unaffected. Returning from the GeoJSON tab fits the map to the drawing; or edit the GeoJSON text directly (one Feature or geometry, or a file of at most 20 MB). A finished drawing carries over to the GeoJSON tab. New grids: code (blank gets an auto code, letters, digits, `-`, `_`, at most 32) and name (1–50 characters) are unique.
- **Import:** a GeoJSON file of at most 20 MB. Each feature must be a Polygon or MultiPolygon with a `name`; `code` is optional. 重名處理 is 覆蓋範圍 (replace only the range) or 略過. Polygon validity and overlap are checked before import, and if any feature fails the whole batch is rejected with the reasons.
- **Validity and overlap:** rings must be closed, have at least 4 points, stay inside the map, have non-zero area, and not cross themselves. Overlap with an existing grid or another feature is rejected above 0.5% of the smaller grid.
- **Edit:** the name, status and range can change; the code is locked. The editor starts from the current range, which is kept unless a new polygon is drawn (the current vertices can be loaded for a single-ring polygon) or the GeoJSON text is changed. A changed range is validated like any other, including overlap with the other grids, and saving it suggests 重新歸屬. 重新導入 (覆蓋範圍) in the import drawer remains an alternative. Disabling shows the object count first; objects keep their grid.
- **Re-assign:** after grid changes, 重新歸屬 updates the grid of existing events and works that have a position, and of 自動 objects (手動 objects are skipped), with a confirm showing the counts. Nothing is re-assigned automatically; an automatic object's grid is always shown live from its position.
